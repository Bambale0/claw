# Задача: провести полный аудит пользовательского опыта и качества frontend

Твоя цель — привести пользовательский интерфейс продукта к состоянию, при котором он ощущается как полностью законченный production-продукт:

- всё работает;
- всё загружается быстро;
- интерфейс понятный без объяснений;
- нет сломанных кнопок;
- нет тупиковых сценариев;
- нет визуальных багов;
- нет скачков интерфейса;
- нет необработанных ошибок;
- нет пустых экранов без объяснения;
- нет действий без обратной связи;
- нет лишних ожиданий;
- UI выглядит цельно и профессионально;
- переходы и состояния работают плавно;
- пользователь всегда понимает, что происходит;
- frontend корректно работает на разных размерах экранов.

Не ограничивайся поверхностным просмотром страниц.

Нужно фактически пройти продукт как реальный пользователь, найти слабые места, исправить их и доказать проверками, что всё работает.

---

# 0. Перед началом

Сначала изучи проект:

1. Прочитай `AGENTS.md`.
2. Прочитай существующую документацию.
3. Изучи frontend-архитектуру.
4. Найди существующие:
   - компоненты;
   - дизайн-систему;
   - UI-kit;
   - стили;
   - роутинг;
   - state management;
   - API-клиенты;
   - обработку ошибок;
   - аналитику;
   - telemetry;
   - frontend-тесты;
   - E2E;
   - CI/CD.
5. Не создавай дублирующие abstractions, если в проекте уже есть подходящий механизм.
6. Не хардкодь данные, URL, состояния, конфигурацию и бизнес-логику.

Перед изменениями зафиксируй текущее состояние и составь план аудита.

# 1. Пройди продукт как пользователь

Проверь все основные пользовательские сценарии от начала до конца.

Не ограничивайся happy path.

Для каждого сценария проверь:

- первый вход;
- повторный вход;
- новый пользователь;
- существующий пользователь;
- пустое состояние;
- заполненное состояние;
- медленный интернет;
- ошибка API;
- timeout;
- повторное нажатие;
- двойной клик;
- обновление страницы;
- back/forward браузера;
- повторное открытие экрана;
- переход по deep link;
- открытие напрямую по URL;
- истёкшие данные;
- отсутствующие данные;
- длинные тексты;
- очень длинные имена;
- отсутствие изображения;
- сломанное изображение;
- повторный запрос;
- отмена действия;
- возврат назад.

Пользователь не должен попадать в состояние, из которого непонятно, что делать дальше.

# 2. Проверить абсолютно все интерактивные элементы

Найди все:

- кнопки;
- ссылки;
- табы;
- dropdown;
- select;
- формы;
- input;
- checkbox;
- radio;
- toggle;
- модальные окна;
- popup;
- drawer;
- меню;
- карточки;
- пагинацию;
- бесконечный скролл;
- upload;
- download;
- copy;
- share;
- delete;
- edit;
- save;
- submit;
- retry;
- back;
- close.

Каждый интерактив должен быть реально нажат и проверен.

Недопустимо:

- кнопка выглядит активной, но не работает;
- кнопка работает со второго раза;
- после клика ничего не происходит;
- можно отправить запрос несколько раз;
- отсутствует loading state;
- modal невозможно закрыть;
- overlay остаётся висеть;
- loader зависает;
- кнопка становится навсегда disabled;
- link ведёт на 404;
- неправильный redirect;
- действие произошло, но UI не обновился;
- UI обновился, но backend-действие не произошло;
- optimistic update оставил неправильное состояние.

Если элемент существует — он должен работать.

---

# 3. UX-аудит

На каждом экране ответь на вопросы:

1. Понятно ли пользователю, где он находится?
2. Понятно ли, что здесь можно сделать?
3. Понятно ли главное действие?
4. Не приходится ли искать нужную кнопку?
5. Есть ли лишние действия?
6. Есть ли лишний текст?
7. Есть ли элементы, которые выглядят кликабельными, хотя ими не являются?
8. Есть ли кликабельные элементы, которые не выглядят кликабельными?
9. Есть ли неоднозначные названия?
10. Есть ли тупиковые состояния?
11. Есть ли unnecessary friction?
12. Можно ли сократить путь пользователя?
13. Получает ли пользователь обратную связь после каждого действия?

Интерфейс должен быть очевиден без инструкции.

---

# 4. Состояния интерфейса

Для каждого async-действия должны быть корректно реализованы:

`idle → loading → success / empty / error → retry`

Проверь:

### Loading

Никаких:

- пустых белых экранов;
- зависшего интерфейса;
- непонятного ожидания.

Используй где уместно:

- skeleton;
- spinner;
- progress;
- disabled state;
- optimistic feedback.

### Empty state

Если данных нет:

- экран не должен выглядеть сломанным;
- нужно объяснить, почему пусто;
- если возможно — предложить следующее действие.

### Error state

Пользователь не должен видеть:

- stack trace;
- `[object Object]`;
- raw JSON;
- HTTP-код без объяснения;
- внутренний текст backend exception.

Ошибка должна:

- быть понятной;
- быть локализованной;
- не ломать весь экран;
- давать возможность retry, если это имеет смысл.

---

# 5. Визуальное качество

Проведи pixel-level визуальный аудит.

Проверить:

- spacing;
- padding;
- margin;
- grid;
- alignment;
- размеры элементов;
- typography;
- font-weight;
- line-height;
- border-radius;
- shadows;
- иконки;
- изображения;
- карточки;
- кнопки;
- формы;
- таблицы;
- модальные окна;
- dropdown;
- overlays.

Особенно искать:

- элементы на 1–5 px съехавшие относительно остальных;
- разные отступы у одинаковых компонентов;
- разные радиусы;
- разные размеры одинаковых кнопок;
- inconsistent typography;
- текст, который обрезается;
- overflow;
- горизонтальный скролл;
- прыгающую высоту карточек;
- некрасивые переносы;
- перекрытие элементов;
- элементы за viewport;
- неправильный `z-index`;
- layout shift.

Одинаковые сущности должны выглядеть одинаково.

---

# 6. Плавность интерфейса

UI должен ощущаться быстрым даже там, где backend отвечает не мгновенно.

Проверить:

- hover;
- focus;
- active;
- pressed;
- disabled;
- loading;
- transition;
- opening/closing modals;
- dropdown;
- navigation;
- skeleton → content;
- появление изображений.

Убрать:

- резкие скачки;
- дергание layout;
- мигание;
- двойные render;
- flash неправильного состояния;
- необоснованные animation;
- слишком длинные transition.

Анимация должна помогать понимать интерфейс, а не тормозить его.

---

# 7. Скорость загрузки

Проведи performance-аудит.

Проверить:

- First Contentful Paint;
- Largest Contentful Paint;
- CLS;
- INP;
- TTFB;
- размер JS bundle;
- количество запросов;
- waterfall;
- duplicate requests;
- unnecessary refetch;
- blocking resources;
- размер изображений;
- lazy loading;
- preload;
- caching;
- compression.

Искать:

- огромные bundle;
- libraries, загружаемые ради одной функции;
- неиспользуемый JS;
- неиспользуемый CSS;
- render-blocking resources;
- изображения оригинального размера там, где нужен thumbnail;
- последовательные API-запросы, которые можно выполнять параллельно;
- повторные запросы одного ресурса;
- N+1 на frontend;
- лишние rerender;
- memory leaks.

Не оптимизируй только synthetic benchmark.

Главная метрика — реальное ощущение скорости пользователем.

---

# 8. API и сеть

Открой Network и проверь реальные запросы.

Не должно быть скрытых:

- `400`;
- `401`;
- `403`;
- `404`;
- `405`;
- `409`;
- `422`;
- `429`;
- `500`;
- `502`;
- `503`;
- timeout;
- CORS errors.

Проверь:

- abort старых запросов;
- retry policy;
- timeout;
- idempotency;
- duplicate submits;
- race conditions;
- stale responses;
- cancellation при смене страницы;
- корректное восстановление после ошибки.

HTTP 200 сам по себе не означает, что сценарий работает.

Проверяй результат глазами и состояние backend.

# 9. Console

Пройди весь продукт с открытой browser console.

В production-сценариях не должно оставаться:

- React/Vue warnings;
- hydration errors;
- key warnings;
- deprecated API warnings;
- failed resources;
- CORS warnings;
- бесконечных console.log;
- debug output.

Каждую ошибку расследовать.

Не маскировать проблему удалением `console.error`.

# 18. Ошибки frontend/backend

Каждая найденная проблема должна классифицироваться:

- frontend;
- backend;
- API contract;
- infrastructure;
- UX;
- performance;
- data;
- race condition;
- integration.

Не делай костыль на frontend, если корневая проблема находится в backend/API.

Исправляй причину, а не визуальный симптом.

---

# 19. Telemetry

Критические пользовательские сценарии должны быть наблюдаемыми.

Для важных действий должно быть возможно понять:

- пользователь нажал кнопку;
- запрос отправился;
- backend его получил;
- операция завершилась;
- UI получил результат;
- пользователь увидел результат.

Добавь telemetry там, где сейчас невозможно расследовать сбой.

Не логируй секреты и чувствительные данные.

---

# 20. Автоматические тесты

После исправлений должны быть тесты.

Минимум:

### Unit
для сложной frontend-логики.

### Integration
для компонентов, завязанных на API/state.

### E2E
для главных пользовательских сценариев.

### Smoke
для production после deploy.

E2E должны проверять не просто существование страницы, а фактическое действие пользователя.

Пример:

плохой тест:

`страница открылась`

хороший тест:

`пользователь открыл страницу → заполнил форму → отправил → backend принял → UI показал корректный результат`

# 22. Не делать

Запрещено:

- скрывать ошибку;
- отключать функцию вместо исправления;
- хардкодить данные;
- вставлять временную заглушку как постоянное решение;
- оставлять `TODO` вместо исправления критического UX;
- считать задачу завершённой только потому, что build проходит;
- считать HTTP 200 доказательством рабочего UX;
- проверять только happy path;
- рефакторить огромные части проекта без необходимости;
- менять работающий UX только ради субъективной красоты.

# 23. Приоритет исправлений

Исправлять в порядке:

## P0

То, что:

- блокирует пользователя;
- ломает основную функцию;
- приводит к потере данных;
- приводит к неправильной оплате/операции;
- вызывает crash;
- делает продукт недоступным.

## P1

- сломанные кнопки;
- ошибки API;
- неправильные состояния;
- dead ends;
- сильные performance-проблемы;
- плохой mobile UX.

## P2

- визуальная несогласованность;
- spacing;
- typography;
- transitions;
- мелкие UX-улучшения.

## P3

- polish;
- микроанимации;
- косметические улучшения.

Сначала надёжность. Потом красота.

# 24. Definition of Done

Работа считается законченной только когда:

- основные user flows пройдены вручную;
- все кнопки и интерактивы проверены;
- нет известных broken actions;
- нет критических console errors;
- нет необъяснимых network errors;
- loading states работают;
- error states работают;
- empty states работают;
- double-click защищён;
- responsive проверен;
- mobile проверен;
- интерфейс не прыгает;
- нет очевидного layout shift;
- нет визуально сломанных экранов;
- frontend не делает лишние запросы;
- нет очевидных performance bottlenecks;
- тесты зелёные;
- E2E зелёные;
- smoke зелёный;
- production после deploy проверен;
- telemetry позволяет расследовать проблемы.

---

# 25. Финальный проход

После всех исправлений не останавливайся сразу.

Сделай полный повторный проход продукта с чистой сессии пользователя:

`вход → основные действия → вторичные действия → ошибки → возврат → повторный вход`

Затем повтори critical path на мобильном размере.

Проверь Network и Console ещё раз после финальных изменений.

Исправь найденные регрессии.

# Главный принцип

Не стремись просто сделать интерфейс «красивым».

Нужно добиться состояния:

**пользователь открывает продукт, мгновенно понимает что делать, всё реагирует на его действия, ничего не ломается, ничего не раздражает, всё работает быстро, предсказуемо, плавно и профессионально.**

Смотри на продукт глазами пользователя, а не разработчика.

Если пользователь способен заметить проблему — это проблема.

Если кажется, что элемент может сломаться — проверь его.

Если сценарий не проверен — не считай его рабочим.

Если ошибка произошла один раз — найди root cause, а не списывай её на случайность.

После исправлений обязательно проведи повторный полный аудит, чтобы убедиться, что исправление одной проблемы не создало другую.
